# 多账号环境与功能设计评估

## 目标和边界

以账号配置隔离和资源开销可控为目标。独立的 Chromium 数据目录只能隔离本地登录数据，不能保证网络、系统指纹或账号之间不可关联。任何网络保护均须覆盖 Claude 主进程、子进程及其 DNS 查询，并在断线后持续生效；单次启动检查或设置代理环境变量不能满足此要求。

## 网络架构建议

优先支持外部、用户自选的代理客户端，并为每个账号保存代理配置及连接检测结果。默认不捆绑 Clash 核心：这避免每个账号多一个常驻进程及代理配置、更新和许可负担；将来如需一键配置，可做可选的、共享的独立核心，而非每账号一个核心。多个账号的上游和出站规则需要可明确区分，不能只共享一个未经隔离的系统代理。

“代理不可用不启动”应是显式选项，启动前通过指定代理访问受控 HTTPS 检测地址，验证实际出口并设置超时；不能只检测端口是否监听，也不能因检测失败而回退直连。启动检查不是断线保护：若要求严格防泄露，需要系统级防火墙或隔离网络环境，阻止相关进程直连，包括 UDP、DNS 和子进程，且要考虑外部浏览器登录与管理员权限。未经端到端验证前，界面不能标注为已防泄露。SOCKS/HTTP 的域名解析位置不同，需以实际客户端行为验证远端解析；仅配置 DNS 服务器并不等于防 DNS 泄露。

## 时区和环境

按账号保存 IANA 时区与语言，并检验其是否与出口区域相符。先做兼容性实验：Windows 原生 API、Electron/Chromium、Node 与子进程未必共同遵循 TZ，不能宣称仅设置 TZ 即可完整隔离。若需强保证，应考虑独立 Windows 用户或虚拟机；不修改全局系统时区。避免随机化彼此不一致的环境信息，也不承诺绕过平台风控。

## 数据与窗口

桌面端官方用量需要先确认受支持的数据来源、授权方式和可用字段；不能把本地 Claude Code 日志当成桌面用量或账单。按需刷新，缓存结果，避免持续扫描和后台轮询。

参考项目的迁移针对桌面端 Claude Code 会话索引，而非所有云端聊天：索引保存在 profile 的 claude-code-sessions 下，实际记录另存。实现前需验证 Store 重定向、目标账号身份及活动文件一致性，列出预览，复制而非移动，禁止覆盖，报告跳过/失败；多个目标身份不能靠猜测选取。不得为迁移自动关闭运行中的账号。

Windows 任务栏按窗口 AppUserModelID 分组。参考项目通过窗口属性、独立图标和任务栏按钮重建实现；应以账号稳定 ID 为分组标识，配色/字母作为视觉标记。仅在启动或发现窗口时短暂处理，不为每个账号保留常驻进程；需要兼容 Store 版、更新和固定到任务栏。窗口位置重叠与任务栏分组是独立问题，应分别验证，不能以修改分组冒充窗口自动排布。

## 验证原则

在独立测试数据目录和受控网络中验证代理掉线、DNS、IPv4/IPv6、子进程和浏览器登录；采集多账号下切换器及 Claude 进程树的内存基线。功能未经过验证前不能声称完全隔离或防泄露。不关闭用户当前运行的实例。
